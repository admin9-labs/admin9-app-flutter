# 模块化地方融媒体 Flutter App 基座增量计划

## 文档状态

- 状态：Active plan
- 日期：2026-07-28
- 适用仓库：`admin9-app-flutter`
- 产品与架构边界的 Source of truth：[`../../DESIGN.md`](../../DESIGN.md)
- 本文职责：描述从当前“西昌发布”静态原型演进为可配置地方融媒体 App 基座的增量实施路径，不改变当前代码行为。

## 目标

本项目旨在建设一个以“西昌发布”为默认实例、具备可复用基础设施和地方融媒体行业核心能力的 Flutter App 基座，并通过可配置原生模块与 H5 轻应用支持不同客户和持续扩展。

这不是把现有产品清空成通用 Flutter demo，也不是把所有业务改成 H5。目标是在保持默认西昌实例可运行、可回归的前提下，逐步建立明确的租户、模块、状态、存储和轻应用边界。

## 当前事实与问题

当前仓库已经具备主题、外观偏好、页面壳、Provider 装配、本地存储、首页频道、稿件、直播、爆料、服务、积分、登录和设置等能力，但仍有以下结构性问题：

- 客户品牌和法律信息以“西昌发布”为中心，尚未收敛为单一租户配置来源。
- 应用根部一次性注册全部 Repository、Provider 和 ViewModel，模块启停缺少统一入口。
- 底部导航与页面实现直接绑定，隐藏入口不能保证模块状态和后台能力不启动。
- `AppStateController` 同时管理稿件、直播、爆料、服务、积分等多类状态，所有权和存储命名空间不清晰。
- Feature 之间存在直接引用实现文件的情况，拆卸单一模块会产生连锁修改。
- H5 能力目前围绕具体频道场景实现，尚无通用轻应用清单、可信域和 Bridge 权限模型。
- 当前静态 Repository 和视图模型是原型边界，不能直接当作未来 CMS、会员或远程配置 API 契约。

## 目标架构

### 1. 稳定宿主

稳定宿主负责与具体业务模块无关、但所有模块共同依赖的应用能力：

- Flutter 启动、异常边界和应用生命周期。
- `TenantProfile`、`RemoteAppConfig`、`UserPreferences` 的解析与合并。
- `AppModule` 契约、`ModuleRegistry` 和模块装配顺序。
- 主题、字号、深浅色、全局灰度、通用页面壳和基础可访问性。
- 顶层导航装配、路由入口聚合和深链分发。
- 网络、日志、可观测性、权限、本地存储等共享服务接口。
- 通用 `MiniAppContainer`、Bridge 网关和可信域校验。

宿主只依赖模块公开契约，不导入模块内部页面、ViewModel 或 Repository 实现。

### 2. 地方融媒体行业核心

以下能力定义产品类别，应作为行业核心持续演进：

- 首页信息入口及其稳定页面壳。
- 频道列表、频道管理与频道内容编排。
- 稿件列表、详情、媒体展示和必要的内容状态。
- 与首页、频道、稿件紧密相关的搜索入口和内容跳转契约。

行业核心仍需遵守模块边界。首页不能直接导入直播、爆料或服务的实现页面，而应通过模块目的地、动作协议或注册表请求对应能力。

### 3. 可选原生模块

第一批可选原生模块包括：

- `live`：电视、广播、互动直播、预告与回放。
- `report`：线索列表、爆料表单与处理记录。
- `services`：服务目录、详情、申请和最近使用。
- `points`：签到、任务、积分明细与兑换。

登录/会话、消息、设置等能力应根据实际所有权收敛到稳定宿主能力或独立模块，不能继续由多个 feature 相互导入实现文件。

每个可选原生模块必须能够独立声明入口、路由、依赖、Provider、状态、后台任务和所需权限。未启用模块不得产生运行时副作用。

### 4. H5 轻应用

H5 用于适合 Web 交付、需要快速更新或由外部系统承载的业务，但不是默认替代原生页面。典型候选包括活动页、专题工具、第三方办事入口和低频客户定制能力。

所有 H5 轻应用统一通过 `MiniAppContainer` 打开，不允许 feature 自行创建无约束 WebView。容器负责可信域、导航策略、Bridge、登录态交换、错误页、加载态、审计和生命周期。

## 三类配置

### TenantProfile

`TenantProfile` 表示随应用或受控客户包交付的租户身份与默认能力，是品牌和法律信息的单一事实来源。

建议字段范围：

- `tenantId`、`displayName`、简称和默认语言。
- App Logo、启动图、顶部视觉资源及主题 token 引用。
- 许可证、备案号、协议、隐私政策、联系地址和举报信息引用。
- 默认启用模块、默认导航顺序和默认首页频道策略。
- API 环境标识、可信域集合和证书/安全策略引用；不得包含明文密钥。
- 配置 schema 版本和最低兼容 App 版本。

“西昌发布”是默认 `TenantProfile`。客户名称、Logo、许可证、协议和地址不得继续散落在通用代码、通用 Widget 或其他模块 fixture 中。

### RemoteAppConfig

`RemoteAppConfig` 表示服务端下发且通过 schema、版本和完整性校验的运行时配置。

建议字段范围：

- 配置版本、发布时间、过期时间、最低/最高兼容 App 版本。
- 已打包原生模块的启停、排序、入口文案和有限展示参数。
- H5 轻应用清单、入口、可信域、Bridge 能力授权和版本要求。
- 运营时间窗、灰度条件、维护状态和紧急下线开关。
- 可被远程覆盖的主题/内容参数白名单。

约束：

- 只能选择安装包中已注册的原生模块，未知模块 ID 必须拒绝或忽略并记录。
- 不能下载、解释或执行新的 Dart 代码，不能修改证书信任、平台权限或原生签名边界。
- 必须保留 last-known-good 配置；拉取失败、校验失败或版本不兼容时回退到已验证缓存或 `TenantProfile` 默认值。
- 配置应用必须可观测，记录版本、来源、校验结果和实际启用模块，但不得记录令牌或敏感个人信息。

### UserPreferences

`UserPreferences` 只保存用户可自主决定的本地偏好，例如：

- 深浅色、字号、全局灰度和无障碍偏好。
- 频道排序、已读提示、搜索历史和最近使用入口。
- 用户主动授权的通知或个性化开关。

用户偏好不能启用租户或远程配置禁用的模块，不能扩大 H5 Bridge 权限，也不能覆盖许可证、可信域和安全策略。所有 key 按 `tenantId + userId/anonymous + moduleId` 分区，避免换租户、换账号或模块卸载后串数据。

### 合并优先级

运行时有效配置按以下顺序求交集和覆盖：

1. 安装包能力清单定义物理上可用的原生模块和平台权限。
2. `TenantProfile` 给出该客户的默认品牌、法律信息和模块集合。
3. 已验证的 `RemoteAppConfig` 只能在允许范围内收窄、启停或调整已打包能力。
4. `UserPreferences` 只能在前三层允许的范围内表达个人偏好。

任何后置层都不得扩大前置层的能力或安全边界。

## AppModule 与 ModuleRegistry

### AppModule 契约

每个模块通过稳定公开契约描述自身，建议至少包含：

- 唯一且稳定的 `moduleId`、模块版本和能力类型。
- 所需宿主能力、平台权限和其他模块公开能力。
- 可贡献的导航入口、路由描述和深链处理器。
- Provider/Repository/ViewModel 工厂，而不是已经启动的全局实例。
- 后台任务声明及其启动、暂停、销毁钩子。
- 模块状态和本地存储命名空间。
- 配置 schema、默认值、校验器和诊断信息。

模块对外只暴露公开契约或宿主可理解的目的地/动作。Feature 不得导入另一个 feature 的 `views/`、`view_models/`、`data/` 等实现文件。

### ModuleRegistry 职责

`ModuleRegistry` 是原生模块的唯一装配入口：

1. 收集安装包内静态注册的 `AppModule`。
2. 校验模块 ID 唯一性、依赖关系、最低版本和平台能力。
3. 根据有效配置计算启用模块集合和稳定顺序。
4. 只为启用模块创建 Provider、Repository、路由、导航入口和后台任务。
5. 向宿主暴露只读模块目录、目的地解析和诊断快照。
6. 在配置变化时执行受控启停；不支持安全热停的模块延迟到下次启动生效。

禁用模块的验收语义是：入口不存在、路由不可解析、Provider 未创建、状态未加载、存储未打开、订阅和后台任务未启动。仅通过 `Visibility`、空页面或权限拦截隐藏入口不算完成。

## 状态与存储拆分

### 状态所有权

逐步拆分当前全局状态，目标所有权如下：

- 宿主状态：当前 tenant、有效配置版本、模块目录、生命周期和全局错误边界。
- 外观与用户偏好：主题、字号、灰度及明确的跨模块用户设置。
- 会话状态：登录身份、令牌状态和授权摘要，通过稳定 `SessionAccess` 接口提供。
- 行业核心状态：首页频道偏好、稿件阅读/收藏等由对应核心能力所有。
- 模块状态：直播预约、爆料记录、服务最近使用、积分账户分别归属各模块。

不新建一个更大的全局 Controller 来替换旧 Controller。页面通过自己的 ViewModel 消费 Repository 或公开能力，Repository 继续作为其数据类型的单一事实来源。

### 存储边界

- 共享存储服务只提供底层 key-value、文件或数据库能力，不理解业务字段。
- 每个模块通过 Repository 拥有自己的序列化、迁移和清理策略。
- key 必须包含 schema 版本和模块命名空间；用户数据还需区分 tenant 与账号。
- 迁移采用“兼容读取旧 key、验证后写入新 key、保留一个回退版本、后续单独清理”的顺序。
- 禁用模块默认不删除用户数据；是否清理由产品策略和隐私要求另行决定。
- 日志、远程配置缓存和 Bridge 审计数据设置明确保留期，不与用户偏好混存。

## MiniAppContainer 与受控 Bridge

### MiniAppContainer

通用容器至少负责：

- 仅加载配置清单中的 HTTPS 初始 URL，开发环境例外必须显式且不可进入生产 profile。
- 对主文档跳转、重定向、新窗口、下载和外部 Scheme 分别执行策略判断。
- 每次跨 origin 后重新计算信任和 Bridge 授权，不沿用上一页面权限。
- 提供统一加载、错误、离线、超时、返回、标题和关闭行为。
- 隔离 Cookie、缓存和本地存储策略；敏感轻应用按 tenant/miniApp 分区。
- 在退出、切后台、模块禁用或账号切换时执行明确的生命周期回收。

### 可信域

- 可信域由 `TenantProfile` 给出上限，`RemoteAppConfig` 只能从中选择或使用经过独立签名发布流程批准的扩展集合。
- 域名匹配使用规范化 host 和明确的子域规则，不使用字符串前缀或包含判断。
- IP、非标准端口、明文 HTTP、证书错误和未批准重定向默认拒绝。
- 可信主文档不自动意味着所有 iframe、弹窗、下载和外部跳转都可信。

### 版本化 Bridge

Bridge 采用显式版本，例如 `admin9.bridge.v1`，消息必须包含 `requestId`、`method`、`version` 和结构化参数。

能力按轻应用逐项授权，例如：

- `navigation.openNativeDestination`
- `session.requestScopedToken`
- `device.getSafeInfo`
- `media.pickImage`
- `share.openSystemSheet`

默认拒绝未声明方法，并对参数 schema、消息大小、调用频率、页面 origin 和生命周期状态进行校验。Bridge 不暴露任意 Dart 方法、任意文件路径、原始长期令牌、任意网络代理或动态代码执行能力。敏感操作需要用户确认或系统权限时，必须由原生侧完成确认。

Bridge 返回结构化成功/错误响应，记录去敏后的 capability、origin、结果和耗时。版本不兼容时显示明确升级或降级提示，不静默放宽权限。

## 远程配置生命周期

1. App 以安装包能力清单和默认 `TenantProfile` 启动。
2. 读取并校验 last-known-good 配置，在兼容时应用。
3. 后台拉取新配置，完成传输安全、签名/完整性、schema 和版本校验。
4. 计算配置差异；仅对声明支持安全热更新的展示参数或模块执行即时变更。
5. 涉及 Provider、路由、后台任务或平台能力的变化默认下次冷启动生效。
6. 新配置导致启动失败时回滚 last-known-good，并上报去敏诊断。

远程配置不是发布系统的替代品。新增原生能力、修改 Dart 逻辑、增加平台权限、升级 Bridge 原生实现或改变安全边界都必须重新构建、签名和发布 App。

## 增量迁移阶段

以下排期按 1 名熟悉现有代码的 Flutter 工程师、现有静态原型持续可运行、产品/设计可及时确认计算；不包含真实 CMS/BFF、第三方 SDK、应用商店审核和多客户正式交付。

### 阶段 0：文档与基线（1-2 天）

- 完成目标、术语、不变量和迁移计划定向。
- 记录默认西昌实例关键行为、现有本地 key 和模块依赖清单。
- 不修改运行时代码。

验收：文档链接有效，目标和非目标无冲突，后续代码阶段有明确边界。

### 阶段 1：TenantProfile（3-5 个工作日）

- 定义最小 `TenantProfile` 和西昌默认 profile。
- 先迁移 App 名称、Logo、许可证、协议、联系地址和现有品牌资源引用。
- 增加配置 schema、校验和默认回退测试。
- 不改变导航、模块启停和现有页面行为。

验收：通用代码不再新增西昌硬编码；切换测试 profile 可替换品牌/法律信息；默认西昌截图和关键流程保持不变。

### 阶段 2：AppModule / ModuleRegistry（5-8 个工作日）

- 定义最小模块契约和静态注册表。
- 先让现有五个顶层入口通过注册结果装配，但默认全部保持当前西昌行为。
- 逐个收敛跨 feature 跳转为稳定目的地/动作契约。
- 添加禁用模块不注册入口、路由、Provider 和后台任务的测试。

验收：至少一个可选模块可完整禁用；未知或不兼容模块配置被拒绝；默认 profile 行为不变。

### 阶段 3：全局状态与存储拆分（8-12 个工作日）

- 按功能从 `AppStateController` 迁移直播、爆料、服务和积分状态。
- 为会话、用户偏好、行业核心和各模块建立明确接口及命名空间。
- 逐批迁移旧 key，每批都有向后读取、回滚和数据隔离测试。
- 每完成一个模块即验证禁用状态不会初始化对应数据链路。

验收：全局 Controller 不再持有已迁移模块的业务状态；tenant/账号/模块数据不串用；迁移前用户数据可读取。

### 阶段 4：通用 H5 容器与 Bridge（8-12 个工作日）

- 将现有频道 H5 能力抽取为 `MiniAppContainer`，先保持当前 H5 行为。
- 实现可信域、重定向策略、轻应用 manifest、能力授权和 Bridge v1。
- 增加恶意 origin、未授权 capability、超大消息、版本不兼容和生命周期测试。
- 选择一个低风险 H5 场景验证，不批量迁移原生页面。

验收：未授权域无法获得 Bridge；授权可审计；容器错误/离线/退出行为一致；默认西昌 H5 场景不回退。

### 阶段 5：RemoteAppConfig（5-8 个工作日）

- 定义远程配置 schema、校验、缓存、过期和 last-known-good 策略。
- 接入模块启停、入口排序和 H5 manifest 的受控配置。
- 增加冷启动生效、热更新白名单、失败回滚和诊断。
- 在没有正式服务端前可使用签入 fixture 或本地受控 mock 验证契约。

验收：远程配置不能启用未打包模块；坏配置不影响启动；回滚可验证；配置变化不执行新 Dart 代码。

### 粗略总排期

按阶段顺序实施时，完成上述基础迁移预计 30-47 个工作日，约 6-10 周。若多人并行，必须先拆清文件和模块所有权，不能并行修改应用装配、全局状态等共享入口。跨端 API、Admin 配置器、生产签名配置、第三方 SDK、真实多租户验收和应用商店发布需要独立估算，不能包含在这一基础排期中。

## 总体验收矩阵

| 维度 | 必须满足 |
|---|---|
| 默认实例 | 西昌发布现有可见行为和本地数据保持不变，差异均有产品决定和迁移说明 |
| 租户 | 品牌、Logo、许可证、协议、地址从 `TenantProfile` 读取，通用代码无新增客户硬编码 |
| 行业核心 | 首页、频道、稿件持续可用，且不直接依赖可选模块实现 |
| 模块禁用 | 入口、路由、Provider、状态、存储加载和后台任务均不启动 |
| Feature 边界 | 不存在 feature 对另一个 feature 实现目录的直接 import |
| 远程配置 | 只控制已打包能力；坏配置可回滚；未知字段和模块有明确处理 |
| H5 | 可信域、重定向、能力授权、Bridge 版本和审计均有自动化覆盖 |
| 存储 | tenant、账号、模块命名空间明确，旧数据迁移可回滚 |
| 质量 | 每阶段通过格式化、静态分析、相关单元/Widget 测试和默认实例浏览器/真机 smoke |

## 风险与控制

| 风险 | 控制措施 |
|---|---|
| 模块化同时改变 UI 行为 | 每阶段以默认西昌实例为回归基线，结构迁移与产品改版分开提交 |
| 隐藏入口但后台仍运行 | 以注册表创建边界为准，测试 Provider、订阅、播放器和后台任务未实例化 |
| `TenantProfile` 变成无边界万能配置 | 固定 schema 和所有权，只放租户身份、品牌、法律信息及安全上限 |
| 远程配置扩大原生权限 | 安装包能力清单是硬上限，未知模块/能力拒绝，敏感变化只在新版本生效 |
| H5 Bridge 泄露会话或设备能力 | scoped token、origin 复核、逐项授权、结构校验、限流和去敏审计 |
| 状态拆分丢失历史数据 | 兼容读、验证写、版本化 key、回滚窗口和迁移 fixture 测试 |
| 大规模移动导致 review 失真 | 先建立契约和装配点，再按模块小批迁移，不先重排全部目录 |
| 多客户需求污染行业核心 | 新需求先判断属于宿主、行业核心、可选原生模块还是 H5 轻应用 |

## 非目标

本计划明确不包含：

- 不先大规模移动现有目录。
- 不引入动态 Dart、脚本解释器或远程代码执行。
- 不把所有页面改为 H5；高频、强交互、媒体播放和系统能力优先保留原生。
- 不立即拆成多个 Dart/Flutter package。
- 不立即迁移到 `go_router` 或其他路由框架。
- 不在没有契约的情况下接入真实 CMS、会员、支付、短信、推送或第三方登录。
- 不把当前静态 `PageBlock`、Repository fixture 或 `RemoteAppConfig` 草案直接当作后台正式 API。
- 不在本阶段改动 `admin9-app-admin`、`admin9-app-uniapp` 或工作区级交付边界。

## 每阶段交付纪律

- 每阶段先列出默认西昌实例行为清单和涉及的存储 key，再开始代码修改。
- 优先新增契约和测试，再迁移一个最小垂直切片；禁止同时重写导航、状态、存储和页面视觉。
- 提交保持单一目的，结构迁移与产品行为变化分离。
- Flutter 代码阶段至少执行 `dart format --output=none --set-exit-if-changed lib test`、`flutter analyze`、相关定向测试和完整 `flutter test`。
- 涉及可见 UI、H5 或模块启停时，补充默认西昌 profile 与至少一个测试 profile 的浏览器/真机 smoke。
- 每阶段完成后更新本文状态、已知风险和下一阶段入口条件。
